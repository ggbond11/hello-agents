# 第四章 智能体经典范式构建

> 本章从零实现三种经典智能体范式：**ReAct、Plan-and-Solve 和 Reflection**。重点不是调用某个框架，而是理解如何组织大语言模型的决策、工具执行、状态传递与迭代纠错。
>
> 参考：[Hello-Agents 第四章：智能体经典范式构建](https://datawhalechina.github.io/hello-agents/#/./chapter4/第四章%20智能体经典范式构建)

## 一、本章主线：从“模型回答”到“智能体解决问题”

普通 LLM 调用通常是“输入问题 → 生成答案”；智能体则在模型之外增加工具、状态和控制流程，使其能够获取外部信息、分解任务、执行操作并改进结果。

可以把本章的智能体系统理解为：

```text
智能体 = LLM + 提示词/输出协议 + 工具（按需）+ 状态/记忆 + 流程控制
```

三种范式分别解决不同问题：

- **ReAct：下一步应该做什么？** 根据最新观察，边推理边行动。
- **Plan-and-Solve：整个任务应该怎样拆解？** 先生成完整计划，再逐步求解。
- **Reflection：当前结果还能怎样改进？** 对已有方案进行评审，再根据反馈修订。

从零实现的意义在于看清框架背后的机制，尤其是输出解析、工具调度、上下文管理、异常处理和终止条件，而不是只掌握框架接口。

## 二、4.1 环境准备与基础组件

### 2.1 依赖和配置

教程建议使用 Python 3.10 或更高版本，基础依赖为：

```bash
pip install openai python-dotenv
# ReAct 搜索案例额外使用 SerpApi
pip install google-search-results
```

通过 `.env` 管理配置，主要变量包括：

| 变量 | 用途 |
| --- | --- |
| `LLM_MODEL_ID` | 模型标识 |
| `LLM_API_KEY` | 模型服务密钥 |
| `LLM_BASE_URL` | OpenAI 兼容服务地址 |
| `LLM_TIMEOUT` | 请求超时，教程默认 60 秒 |
| `SERPAPI_API_KEY` | 搜索工具密钥，仅搜索案例需要 |

密钥不应硬编码或提交到版本库。`.env` 只是配置加载方式，本身不等于访问控制或加密机制。

### 2.2 统一封装模型客户端

教程用 `HelloAgentsLLM` 封装底层调用：

1. 用 `load_dotenv()` 加载配置，允许构造参数覆盖环境变量。
2. 检查模型、密钥和服务地址是否齐全。
3. 创建 `OpenAI` 客户端。
4. 通过 `think(messages, temperature=0)` 提供统一入口。
5. 流式接收响应，将分片拼接为完整文本，供上层解析。
6. 捕获调用异常；上层必须处理空响应或失败结果。

**设计价值：将模型调用与智能体控制逻辑解耦**，三种范式可以复用同一个客户端。低温度通常有助于输出稳定，但不保证结果绝对确定或正确。

## 三、4.2 ReAct：思考—行动—观察

### 3.1 核心机制

**ReAct（Reasoning and Acting）**把推理与外部行动交替组织起来：

```text
用户问题 + 历史记录
        ↓
Thought：分析当前情况，决定下一步
        ↓
Action：选择工具及参数
        ↓
程序执行工具，产生 Observation
        ↓
将行动和观察写入历史，再次调用模型
        ↓
……直到 Finish[最终答案] 或达到步数上限
```

- **Thought**：教程中用于表达当前分析和行动意图的文本。
- **Action**：模型提出的操作请求，例如 `Search[查询内容]`。
- **Observation**：程序实际执行工具后返回的信息，不是模型自行编造的结果。
- **Finish**：终止协议，表示输出最终答案，不是搜索等外部工具。

**关键分工：模型负责决定行动，程序负责执行行动，工具结果再反馈给模型。** 日志可以帮助追踪行为，但模型生成的解释并不等同于其内部计算过程的忠实记录。

### 3.2 为什么不只使用思维链

- 仅依赖思维链，可以拆解推理，但无法自动获得实时外部信息，也不能直接执行操作。
- 仅生成动作，缺乏对任务目标、历史结果和错误的持续分析。
- ReAct 将两者结合：**推理指导行动，行动结果为后续推理提供依据**。

工具可以缓解知识过时、计算错误等问题，但工具结果也可能不完整或错误，并不能彻底消除幻觉。

### 3.3 工具定义与执行器

教程把工具拆成三个要素：

1. **名称**：唯一调用标识，如 `Search`。
2. **描述**：说明用途，帮助模型判断何时调用。
3. **执行逻辑**：真正执行任务的函数。

`ToolExecutor` 负责统一管理工具：

| 方法 | 职责 |
| --- | --- |
| `registerTool` | 注册工具名称、描述和函数 |
| `getAvailableTools` | 生成可写入提示词的工具说明 |
| `getTool` | 根据模型给出的名称找到执行函数 |

搜索示例使用 SerpApi，优先提取答案摘要等直接信息，其次提取知识图谱描述，最后返回少量常规搜索结果摘要。这样可以减少无关内容，降低上下文开销。

### 3.4 ReActAgent 实现要点

- **提示词**：注入工具清单、原始问题、历史记录，约束 `Thought` / `Action` 格式。
- **解析器**：先分离 `Thought` 与 `Action`，再从 `工具名[参数]` 中提取调用信息；教程使用正则表达式。
- **执行循环**：调用 LLM → 解析 → 判断是否结束 → 查找并执行工具 → 记录观察。
- **历史状态**：保存交互过程，让下一轮决策能利用前面的结果；每次新任务应重置历史。
- **终止保护**：收到 `Finish` 正常结束，或到达 `max_steps` 上限停止，避免无限循环。

### 3.5 优势、局限和调试

**适用场景**：实时信息查询、探索式检索、多工具协作、需要根据环境反馈改变路线的任务。教程以搜索“华为最新手机”相关信息为例，不应把示例搜索结果当作长期有效的事实。

**优势**：动态调整、可追踪性强、工具与模型协同。

**局限**：多轮串行调用增加成本；依赖模型遵循输出格式；缺少全局规划时可能陷入局部最优或重复操作。

**调试顺序**：检查最终提示词 → 查看模型原始输出 → 核对解析结果 → 验证工具输入与输出 → 必要时增加少样本示例、调整模型或参数。实际记录日志时应脱敏。

## 四、4.3 Plan-and-Solve：先规划，后执行

### 4.1 核心机制

将任务明确拆为两个阶段：

```text
问题 → Planner 生成完整计划 → Executor 按顺序求解 → 最终答案
                                      ↑
                              历史步骤及其结果
```

- **Planner（规划器）**：把复杂问题拆成粒度合适、可执行、按依赖顺序排列的步骤。
- **Executor（执行器）**：专注当前步骤，利用已有结果完成求解。
- **PlanAndSolveAgent**：协调两者，体现“组合优于继承”。

与 ReAct 的区别在于：ReAct 依据每次观察决定下一步；本章 Plan-and-Solve 实现先确定完整计划，再按计划执行，**没有自动重规划机制**。

### 4.2 结构化计划与解析

教程要求规划器输出 Python 字符串列表，例如：

```python
["计算周二销量", "计算周三销量", "计算三天总销量"]
```

程序提取代码块后，用 `ast.literal_eval()` 将字面量解析为列表，并处理格式错误和空计划。

**不要用 `eval()` 执行模型输出。** `ast.literal_eval()` 不执行任意 Python 表达式，但工程上仍需校验列表是否非空、每个元素是否为有效字符串，以及计划长度是否合理。

### 4.3 执行器的关键：状态传递

每一步的提示词包含四类信息：

1. **原始问题**：保持最终目标不变。
2. **完整计划**：说明当前步骤在全局中的位置。
3. **历史步骤与结果**：提供已完成工作的输出。
4. **当前步骤**：约束模型只解决当前子任务。

执行后，将“步骤 + 结果”追加到历史中，作为后续步骤的输入。教程最终返回最后一步结果，因此计划的最后一步应明确完成汇总或回答原问题。

### 4.4 案例与适用场景

教程的水果销量问题：

```text
周一：15 个
周二：15 × 2 = 30 个
周三：30 - 5 = 25 个
总计：15 + 30 + 25 = 70 个
```

这一案例**不调用外部工具**，重点是展示“任务拆解 → 顺序执行 → 状态传递”，而不是展示数学难度。Plan-and-Solve 本身并不排斥工具，只是本章示例没有集成。

- **优势**：结构清晰、容易检查步骤依赖，适合多步数学推理、流程明确的分析任务。
- **局限**：初始计划错误会影响后续执行；中间结果错误可能逐步传播；固定计划不易适应环境变化。
- **扩展方向**：增加步骤校验、失败重试与重规划，但这些不是本章基础实现已有的能力。

## 五、4.4 Reflection：执行—反思—优化

### 5.1 核心机制

Reflection 不满足于得到第一版答案，而是增加一个评审和修订闭环：

```text
原始任务 → 初始方案
             ↓
          反思/评审 → 达到要求则结束
             ↓
          具体反馈
             ↓
          修订方案 → 再次反思，直到结束或达到迭代上限
```

各阶段职责不同：

- **执行（Execution）**：生成初始代码、答案或方案。
- **反思（Reflection）**：检查事实、逻辑、效率和遗漏约束，给出可操作的反馈。
- **优化（Refinement）**：结合原始任务、上一版方案和反馈进行定向修改，而不是无目标地重新生成。

形式化表示：

```text
Fᵢ = Reflect(Task, Oᵢ)
Oᵢ₊₁ = Refine(Task, Oᵢ, Fᵢ)
```

其中 `Oᵢ` 是第 i 版输出，`Fᵢ` 是针对该版本的反馈。执行、评审和修订可以使用同一模型配不同提示词，不一定需要多个模型或多个独立智能体。

### 5.2 短期记忆 Memory

教程以列表保存执行和反思记录：

| 接口/字段 | 作用 |
| --- | --- |
| `records` | 按顺序保存 `execution`、`reflection` 等记录 |
| `add_record` | 添加方案或反馈 |
| `get_last_execution` | 获取最近一版方案 |
| `get_trajectory` | 将完整轨迹序列化成文本，便于需要时注入上下文 |

**存储了完整轨迹，不等于每轮都传入全部轨迹。** 本章主循环主要取最近代码进行评审，再把最近代码与反馈交给优化阶段。这里的记忆是任务内的短期状态，不是模型训练，也不是自动获得了跨任务长期记忆。

### 5.3 代码优化案例

任务：编写函数，找出 1 到 n 之间的所有素数。

1. 初始方案采用逐个试除，检查每个候选数是否有不大于其平方根的因子。
2. 反思指出性能瓶颈，建议改用**埃拉托斯特尼筛法**。
3. 优化阶段依据反馈改写代码。
4. 再次评审，认为常规场景下已经足够高效，结束迭代。

| 方案 | 时间复杂度 | 主要特点 |
| --- | --- | --- |
| 对每个候选数进行平方根范围试除 | `O(n√n)` 的上界 | 容易实现，但大规模输入时较慢 |
| 埃拉托斯特尼筛法 | `O(n log log n)` | 批量标记合数，典型空间开销为 `O(n)` |

Reflection 的价值不仅是修复语法或功能错误，还可以推动**算法和方案质量的提升**。但本章示例主要由模型生成与评审代码，并未自动执行测试来证明优化后的正确性或实际性能。

### 5.4 终止条件与成本收益

教程使用两个终止条件：

- 反馈中出现“无需改进”。
- 达到 `max_iterations` 上限。

初始生成需要一次模型调用；每个完整的“反思 + 修订”轮次再增加两次调用。如果反思后直接停止，该轮不再执行修订。

- **收益**：有机会发现逻辑漏洞、遗漏约束和性能问题，提高结果质量。
- **代价**：更多 Token、调用费用和串行延迟，还要设计不同阶段的提示词。
- **适用**：高质量代码、技术报告、复杂推演等质量优先且时延要求相对宽松的任务。
- **风险**：同一模型可能重复自身盲点；反思意见也可能有误，多轮修改不保证持续变好。

## 六、三种范式对比与选型

| 维度 | ReAct | Plan-and-Solve | Reflection |
| --- | --- | --- | --- |
| 核心策略 | 边想边做 | 先规划再执行 | 先产出再评审修订 |
| 主要反馈 | 外部工具/环境观察 | 前面步骤的求解结果 | 对当前方案的评审反馈 |
| 计划特点 | 随观察逐步调整 | 本章实现采用固定完整计划 | 重点是改进结果，可叠加在执行流程上 |
| 关键状态 | 行动与观察历史 | 计划、当前步骤、历史结果 | 方案版本与反馈记录 |
| 主要优势 | 适应动态环境 | 结构清晰、步骤有序 | 提升质量、支持自我纠错 |
| 主要风险 | 循环、工具误用、局部最优 | 错误计划和结果逐步传播 | 评审失误、过度修改、成本上升 |
| 典型任务 | 实时搜索、探索、工具协作 | 数学应用题、固定流程分析 | 代码优化、报告审校 |

选择时先看任务瓶颈：

- **缺少外部信息、路线不确定**：优先考虑 ReAct。
- **步骤依赖明确、主要是多步推理**：优先考虑 Plan-and-Solve。
- **初稿容易生成，但质量要求高**：增加 Reflection。

三者并非互斥，可以组合为：**规划器拆解任务 → 每个步骤用 ReAct 调用工具 → 最后用 Reflection 评审并修订**。组合会提高能力，也会增加状态管理、延迟和预算控制的复杂度。

## 七、工程补充：从教学示例到可用系统

> 以下是基于本章实现的延伸建议，不代表教程代码已经具备这些能力。

1. **使用可靠的输出协议**：正则和代码块解析适合学习；生产环境可采用原生工具调用、JSON Schema 或结构化输出，并验证工具名、参数类型及必填字段。
2. **分别处理模型和工具失败**：对空响应、解析失败、超时、限流、无效工具和工具异常制定策略，设置有限重试，避免无上限地重复调用。
3. **同时约束步数、时间和费用**：达到上限不等于任务完成，应明确返回已完成部分、未解决问题和停止原因。
4. **控制上下文增长**：保存可追溯记录，但按需传入历史；可以摘要、筛选或截断旧信息，保留关键约束和证据。
5. **让评审有客观依据**：代码任务结合单元测试、静态检查和性能测量；事实任务核对可靠来源。保留已验证的较好版本，避免修订退化。
6. **改进终止判断**：直接匹配“无需改进”较脆弱，可改为结构化评审状态，并结合测试结果或质量阈值，而不是只相信模型自评。
7. **限制工具权限**：搜索结果和工具返回是外部数据，不应覆盖系统规则；执行代码应隔离，写入、删除或外发等高风险操作应设权限与确认机制。
8. **记录并保护日志**：保留提示词版本、模型输出、工具输入输出、耗时和停止原因以便排查，同时避免泄露密钥及敏感信息。

## 八、复习速记

- **ReAct：思考指导行动，观察修正后续决策。**
- **Plan-and-Solve：规划负责拆解，执行负责求解，历史负责传递状态。**
- **Reflection：先形成方案，再生成反馈，最后根据反馈定向修订。**
- 工具不会因为被写进提示词就自动执行，必须有程序完成解析、校验和调度。
- 反思不是训练，记忆不是模型权重更新，自评通过也不等于客观验证通过。
- 智能体的核心不只是提示词，而是**围绕模型建立可控、有状态、可验证的执行闭环**。
