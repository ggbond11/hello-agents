# 第六章 框架开发实践

> 本章从“手动实现智能体”进一步走向“使用框架构建智能体应用”，通过 AutoGen、AgentScope、CAMEL 和 LangGraph 四个代表性框架，理解多智能体协作、消息驱动、角色扮演以及图工作流等不同技术路径。
>
> 参考：[Hello-Agents 第六章：框架开发实践](https://datawhalechina.github.io/hello-agents/#/./chapter6/%E7%AC%AC%E5%85%AD%E7%AB%A0%20%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5)

## 一、章节主线：为什么需要智能体框架

第四章通过原生代码实现了 ReAct、Plan-and-Solve 和 Reflection，帮助我们理解智能体的执行逻辑；但一次性脚本很难支撑复杂、长期运行、可维护的应用。框架的本质，是把所有智能体都会反复实现的通用能力抽象出来，例如：

- Agent Loop（智能体主循环）与任务调度；
- 状态、上下文和记忆管理；
- 工具定义、注册、调用及错误处理；
- 多智能体之间的消息传递和协作编排；
- 日志、事件回调、追踪与调试；
- 并发执行、容错恢复、持久化和部署。

因此，框架开发的核心收益不是“少写几行代码”，而是让开发者专注于业务目标和角色设计，同时获得更规范的架构、更好的复用性和更强的工程能力。

### 1. 框架化开发要解决的问题

1. **提高复用与开发效率**：复用通用 Agent、执行器、工作流和工具组件。
2. **实现模块解耦**：将模型层、工具层、记忆层、智能体层和流程层分开，便于替换模型或升级组件。
3. **规范状态管理**：处理多轮对话、历史持久化、上下文窗口和长期任务状态。
4. **增强可观测性**：通过回调或事件记录 `on_llm_start`、`on_tool_end`、`on_agent_finish` 等关键节点，追踪完整运行轨迹。

## 二、四种框架的设计哲学

| 框架 | 核心抽象 | 控制方式 | 典型优势 | 更适合的场景 |
| --- | --- | --- | --- | --- |
| **AutoGen** | 可对话的多智能体群聊 | 对话和团队编排 | 角色分工自然，协作流程直观，支持人类介入 | 软件开发团队、多人讨论、流程化协作 |
| **AgentScope** | 消息驱动的智能体平台 | 消息路由、Pipeline 和运行时 | 工程化、异步、并发、分布式、可恢复 | 大规模或长期运行的生产级多智能体系统 |
| **CAMEL** | 角色扮演的智能体社会 | 初始提示引导自主对话 | 轻量、灵活，容易激发深度协作 | 双智能体专家协作、创作、研究和头脑风暴 |
| **LangGraph** | 状态机/有向图 | 节点、边、条件边和循环 | 流程显式、可控、可审计，天然支持反思和回退 | 严格流程、工具链、分支、循环和人机协作 |

可以把它们放在两个互补维度上理解：

- **涌现式协作 ↔ 显式控制**：AutoGen、CAMEL 更多依靠角色、目标和对话规则，让协作行为自然产生；LangGraph 则把每一步和跳转条件明确写出，换取可预测性。
- **原型灵活性 ↔ 生产工程化**：CAMEL/AutoGen 便于快速验证协作想法；AgentScope 更关注并发、容错、分布式部署和全生命周期运维。

## 三、AutoGen：以对话驱动协作

### 3.1 核心机制

AutoGen 把多智能体系统抽象成一组能够对话的角色。任务通过消息在智能体之间流动，智能体根据对话上下文不断协作，直到达到终止条件。0.7.4 版本采用更清晰的分层和异步优先设计：

- `autogen-core`：封装模型交互、消息传递等底层能力；
- `autogen-agentchat`：提供开发对话式智能体和团队的高级接口；
- `AssistantAgent`：封装 LLM，负责思考、规划、编写内容或代码；
- `UserProxyAgent`：代表用户发起任务，也可以执行代码、工具和最终验收；
- `Team` / `RoundRobinGroupChat`：组织参与者并协调群聊。

`RoundRobinGroupChat` 按参与者列表的顺序依次发言，适合“需求分析 → 编码 → 审查 → 测试”这类固定流程。常见的安全控制有：

- `termination_condition`：例如检测 `TERMINATE`；
- `max_turns`：限制最大轮次，防止无限循环和成本失控；
- 异步 `async/await`：等待模型或网络请求时不阻塞其他任务。

### 3.2 软件开发团队案例

案例目标是开发一个用 Streamlit 实时显示比特币价格的 Web 应用，团队包含四个角色：

1. **ProductManager**：澄清需求、拆分功能、选择技术方案并制定验收标准。
2. **Engineer**：根据计划编写可运行代码，考虑异常处理和边界情况。
3. **CodeReviewer**：审查可读性、可维护性、性能、安全性和错误处理。
4. **UserProxy**：代表用户发起需求、执行/验证交付物，并在完成后终止流程。

实现过程的关键不在于类名，而在于高质量的 `System Message`：系统消息应明确角色、职责、输出结构、交接条件和完成标志。模型客户端应独立封装，使用环境变量管理模型名、API Key 和 `base_url`，从而支持 OpenAI 兼容服务以及 DeepSeek、通义等其他模型。对于非 OpenAI 模型，还需要提供 `model_info`，声明函数调用、视觉、结构化输出和上下文长度等能力边界。

### 3.3 优势与局限

**优势**：用对话表达团队协作，降低复杂流程建模门槛；角色职责易复用；`UserProxyAgent` 便于实现 Human-in-the-loop；固定群聊流程清晰。

**局限**：LLM 回复具有不确定性，可能偏题、循环或偏离角色；问题常表现为很长的对话历史，调试难度高；轮询群聊对动态回退、复杂路由和大规模并发并非最优。生产环境应加入轮次、预算、超时、消息长度、质量检查和人工审核等保护措施。

## 四、AgentScope：消息驱动的工程化平台

### 4.1 分层设计

AgentScope 面向大规模、稳定运行的多智能体应用，采用组合式架构和消息驱动模式：

1. **基础组件层**：统一 `Message`、短期/长期 `Memory`、模型 API 和 `Tool`。
2. **智能体基础设施层**：提供预构建智能体、ReAct、钩子、状态管理、并行工具调用、异步执行和实时控制。
3. **多智能体协作层**：`MsgHub` 负责消息路由与状态管理，`Pipeline` 支持顺序、并发等工作流编排。
4. **开发与部署层**：Runtime 提供生产运行环境，Studio 提供可视化工具链。

### 4.2 消息驱动的关键价值

消息是智能体之间交互的统一协议，通常包含发送者、内容、角色和元数据。相比直接函数调用，消息架构具备：

- **异步解耦**：发送方和接收方不必同时在线，便于并发执行；
- **位置透明**：接收者可以在本地进程或远程节点，调用方无需改变；
- **可追踪**：消息可记录、检索和分析，方便监控与调试；
- **可靠性**：消息可以持久化、重试和恢复，提升故障容忍能力。

Agent 的生命周期通常包含初始化、运行、暂停和销毁，开发者主要实现 `reply` 方法，也可以通过 `observe` 将消息写入记忆。`MsgHub` 支持点对点、广播、组播、持久化以及跨进程/跨服务器通信。

### 4.3 “三国狼人杀”案例的启示

狼人杀案例用于展示多角色实时交互、消息广播和并发协作。此类应用中，不应只依赖自然语言约定；应使用结构化输出模型约束角色动作，例如讨论结果、投票、女巫用药等字段，并对枚举值、必填字段和状态转换进行验证。

**适用性**：AgentScope 适合高并发、分布式、需要长期运行和故障恢复的应用；代价是架构和异步消息模型更复杂，开发者需要理解生命周期、消息一致性、顺序性和分布式部署。

## 五、CAMEL：基于角色扮演的自主协作

### 5.1 Role-Playing 与 Inception Prompting

CAMEL 通过给多个智能体设定角色、共同任务和初始引导提示（Inception Prompting），让它们自主展开多轮协作。`RolePlaying` 高级 API 将角色定义、任务描述和对话初始化封装起来，开发者不必手动编写全部提示词。

案例是由“心理学家”和“作家”共同创作《拖延症心理学》电子书：

- 心理学家提供理论、实证研究和专业事实核查；
- 作家负责结构设计、通俗表达、案例和读者体验；
- `init_chat()` 生成开场消息；
- `step()` 驱动一轮双向对话；
- 通过轮次上限或 `<CAMEL_TASK_DONE>` 标志终止。

协作一般经历：目标对齐与框架搭建 → 专业知识生成与通俗转译 → 迭代润色与事实检查 → 总结收尾。

### 5.2 优势与局限

**优势**：代码量少，提示驱动，适合快速验证专家协作想法；角色关系自然，适合研究、创作和开放式任务；生态逐渐支持多模态、工具集成、多模型后端及与其他框架互操作。

**局限**：效果高度依赖角色提示和任务提示的质量，出现问题时不容易定位；双智能体范式扩展到多智能体后，需要额外的路由、状态同步和冲突仲裁；对于严格步骤、复杂决策树和大规模并发，LangGraph、AutoGen 或 AgentScope 可能更合适。应设置最大轮次、完成判定、事实校验和冲突解决机制，避免“自主协作”失控。

## 六、LangGraph：用状态图显式控制工作流

### 6.1 三个基本构件

LangGraph 将智能体执行过程表示为状态机和有向图：

- **State（状态）**：贯穿整个流程的共享数据结构，可用 `TypedDict` 定义，包括消息历史、当前任务、中间结果、步骤标记、迭代次数和最终答案。
- **Node（节点）**：接收状态、完成一个具体计算并返回状态更新的函数，例如调用 LLM、执行工具、生成答案或反思评估。
- **Edge（边）**：决定节点之间的流向。普通边连接固定步骤；条件边根据当前状态动态选择下一节点，并可跳回之前的节点形成循环。

典型流程是：定义状态 → 编写节点 → 添加普通/条件边 → 设置入口和结束节点 → `compile()` → 运行或流式获取事件。每个节点是独立函数，因此便于测试、替换和插入人工审核节点。

### 6.2 三步问答助手

案例将问答拆为三个节点：

```text
START → Understand → Search → Answer → END
```

1. **Understand**：理解用户意图，把自然语言问题总结为 `user_query`，生成更适合搜索引擎的 `search_query`。
2. **Search**：调用 Tavily 等工具搜索，写入 `search_results`；失败时更新 `step`，不要把异常静默吞掉。
3. **Answer**：搜索成功则基于结果回答；搜索失败则走回退策略，并明确告知用户信息来源和局限。

可以配合 Checkpointer 保存状态，实现多轮交互、暂停恢复和调试。通过条件边，还可以添加“答案质量评估”节点：质量不足则回到搜索或生成节点，达到最大迭代次数后转人工审核或结束。

### 6.3 优势与局限

**优势**：流程、状态和跳转显式可见；天然支持循环、反思、修正、回退和人机协作；节点模块化，便于审计和测试；对可靠性要求高的生产工作流更友好。

**局限**：需要编写更多状态、节点和边的样板代码；简单任务可能显得繁琐；显式工作流牺牲了一些对话式协作的动态涌现；调试仍需同时检查节点逻辑、状态变更和路由条件。

## 七、框架选型与工程实践

### 7.1 选型建议

- **需要固定角色按顺序协作**：优先考虑 AutoGen。
- **需要大量并发、分布式部署、持久化和容错**：优先考虑 AgentScope。
- **需要两个或少量专家进行开放式深度讨论/创作**：可考虑 CAMEL。
- **需要可审计的步骤、分支、回退、循环或人工审批**：优先考虑 LangGraph。
- **逻辑简单、框架引入成本高或需要完全掌控底层**：可以保留原生实现。

选型时不要只比较 API 易用性，还要评估：模型兼容性、工具调用能力、状态持久化、并发模型、可观测性、失败恢复、成本控制、部署方式、社区活跃度和团队学习成本。

### 7.2 从原型走向生产的检查清单

1. **边界与终止**：最大轮次、最大 token/费用、超时、取消和明确的结束条件。
2. **状态与数据**：定义状态 Schema，限制上下文长度，持久化关键状态，避免敏感信息泄露。
3. **输出可靠性**：优先使用结构化输出和 Schema 校验；解析失败要重试或进入人工审核。
4. **工具安全**：校验工具参数，设置权限、沙箱、超时和重试；区分模型建议与程序实际执行结果。
5. **可观测性**：记录 trace、节点耗时、模型调用、工具结果、错误和成本，并对日志脱敏。
6. **质量评估**：为每个角色和流程定义验收标准，使用离线数据集、回归测试和人工抽检。
7. **人机协作**：在高风险动作、低置信度结果或流程分歧处设置人工确认节点。
8. **故障恢复**：为网络错误、模型限流、工具失败、消息重复和服务重启设计回退与幂等机制。

## 八、本章总结

本章没有给出唯一的智能体构建方式，而是展示了不同的抽象层次：

- **AutoGen**：把协作看成多角色群聊，重点是“谁与谁对话”；
- **AgentScope**：把协作看成消息系统，重点是工程化、并发和分布式运行；
- **CAMEL**：把协作看成角色扮演社会，重点是通过提示激发自主协作；
- **LangGraph**：把协作看成状态图，重点是显式控制、循环和可审计流程。

最重要的设计权衡是：**涌现式协作带来灵活性，显式控制带来可靠性；原型能力解决“能不能运行”，工程化能力解决“能不能长期稳定服务”。** 实际项目应根据任务开放程度、流程确定性、并发规模、可靠性和审计要求选择框架，而不是盲目追逐某个热门工具。
